# Paper Summary: Towards Seamless Tracking-Free Web: Improved Detection of Trackers via One-class Learning

**Citation:** Muhammad Ikram, Hassan Jameel Asghar, Balachander Krishnamurthy, Mohamed Ali Kaafar, and Anirban Mahanti, 2016, arXiv:1603.06289v1.  
**Source:** `/home/nhatquang/Desktop/HCMUS Course/PhD_Applications/Macquarie_Kaafar/kaafar-papers/pdfs/1603.06289-tracking-free-web.pdf`  
**One-line takeaway:** The paper shows that one-class learning over JavaScript code structure can separate tracking scripts from functional scripts more accurately than popular privacy-preserving browser tools, while requiring only labelled examples of known trackers.

## 1. What Problem Is This Paper Solving?

The paper studies a practical web privacy problem: browser privacy tools often block JavaScript aggressively, but many JavaScript programs are necessary for normal website functionality. If a tool blocks too much, the page breaks and users abandon the tool; if it blocks too little, tracking continues. Existing tools such as NoScript, Ghostery, Adblock Plus, Disconnect, and Privacy Badger rely heavily on blacklists, URL matching, heuristics, or broad blocking policies. These approaches struggle because trackers change, JavaScript can be embedded inline, and domains can host both tracking and functional scripts.

The authors focus on JavaScript-based tracking, including scripts used for advertising, analytics, social widgets, cookies, hidden iframes, and user activity collection. Their goal is not merely to detect known tracking domains, but to classify the JavaScript program itself as tracking or functional. This makes the problem more suitable for machine learning: tracking scripts often reuse similar code patterns, even when variable names, domains, or surrounding page context change.

## 2. Main Contributions

- The paper provides a manually labelled dataset of 2,612 JavaScript programs from 95 websites, using explicit rules for tracking versus functional behavior.
- It evaluates five popular privacy-preserving tools and shows that they do not achieve a strong balance between blocking trackers and preserving functional code.
- It proposes one-class SVM and positive-unlabelled learning approaches using syntactic and semantic JavaScript features, trained only on known tracking scripts.
- It evaluates the classifiers on a larger wild corpus of 135,656 JavaScript programs from 4,084 websites and analyzes disagreements with existing tools, including cases where the classifier identifies trackers missed by blacklists.

## 3. Method Explained

**Intuition:** Tracking JavaScript is often copied, adapted, or generated from recurring analytics, advertising, and social-widget code. Even if the URL, variable names, or exact formatting differ, the script may preserve recognizable structure. Functional JavaScript, such as menus, search boxes, login widgets, content loading, or media embedding, has a different structural profile. The authors use this similarity signal to classify scripts by code content rather than by domain blacklist alone.

**Technical core:**

- The authors crawl pages using Firefox controlled by Selenium, save rendered DOM trees, extract in-page and external JavaScript, and beautify compressed scripts with `jsbeautifier`.
- They manually label JavaScript using 12 rules. Tracking includes ad panels, ad fetching, social media widgets, third-party analytics or advertiser scripts, cookie readers/writers for known tracking domains, and hidden iframes tied to advertising or analytics. Functional includes navigation, search, login, shopping carts, first-party content fetching, CDNs, and local keyboard or mouse event handling when no third-party leakage occurs.
- They extract syntactic features by treating lines of JavaScript as terms and weighting them with tf-idf.
- They extract semantic features by converting JavaScript into canonical form, abstracting away details such as variable names, then constructing sequential n-grams or program-dependency-graph n-grams. They test 4-gram and 7-gram variants.
- They train one-class SVM and positive-unlabelled learning models using only tracking JavaScript as labelled positive examples. A standard supervised two-class SVM is used as a benchmark, but the one-class setup is the practical contribution because collecting exhaustive functional labels is unrealistic.

## 4. Experiments And Results

- **Data:** The labelled dataset contains 2,612 JavaScript programs from 95 websites: 1,376 tracking scripts and 1,236 functional scripts. The wild dataset contains 135,656 JavaScript programs from 4,084 websites.
- **Baselines:** NoScript, Ghostery, Adblock Plus, Disconnect, Privacy Badger, and a supervised two-class SVM benchmark.
- **Metrics:** True positive rate, false positive rate, true/false negatives, accuracy, aggressiveness of blocking, and agreement/disagreement with privacy tools on the wild corpus.
- **Key findings:** On the labelled dataset, NoScript has the highest tracking-blocking true positive rate among the tools at 0.78, but also the worst false positive rate at 0.21. Ghostery has a lower true positive rate, 0.65, but a better false positive rate, 0.08. Adblock Plus, Disconnect, and Privacy Badger have low false positive rates around 0.06 but miss many trackers, with true positive rates of 0.44, 0.40, and 0.37 respectively.
- The machine-learning classifiers perform much better on the labelled data. With sequential 7-gram or PDG 7-gram features, one-class SVM and PU learning reach around 0.98 to 0.99 true positives and 0.98 to 0.99 true negatives, comparable to supervised SVM.
- On the wild dataset, the best classifier's output differs substantially from existing tools: agreement is roughly 75-80 percent with NoScript, Ghostery, and Adblock Plus, but only 36-43 percent with Disconnect and Privacy Badger depending on classifier and feature model.
- The authors manually inspect two 100-script disagreement samples. For scripts the classifier marked as tracking while all tools allowed them, manual labelling agreed with the classifier in 75 cases. For scripts the classifier marked as functional while all tools blocked them, manual labelling agreed with the classifier in 81 cases. This supports the claim that code-structure classification can both discover missed trackers and reduce unnecessary breakage.

## 5. Limitations And Risks

- The labelled dataset is relatively small and manually produced, so rule choices matter. In particular, social widgets are treated as tracking even though some users may perceive them as functional.
- The model can be evaded by trackers that introduce rare, custom code or heavy obfuscation. The authors argue that canonicalization handles variable renaming and whitespace changes, but dummy code and encoded JavaScript remain harder.
- The study validates disagreement samples, not the entire wild dataset, so the large-scale wild results are suggestive rather than fully ground-truthed.
- The classifier can misclassify benign cookie code or comment/statistics code when it structurally resembles tracking code.
- The work is from 2016; modern tracking now includes more sophisticated fingerprinting, consent-management interactions, server-side tagging, browser privacy changes, and anti-adblock behavior. The methodological lesson remains useful, but empirical numbers should not be treated as current browser-tracking performance.

## 6. Why This Matters For Nguyen Nhat Quang's IAM/security-ML PhD Direction

This paper is valuable for an IAM/security-ML PhD direction because it frames security classification as a deployment-sensitive decision, not just a benchmark problem. The authors explicitly optimize for the tradeoff between blocking harmful behavior and preserving legitimate functionality. That same tension appears in IAM anomaly detection: an access-control detector must catch risky behavior without producing so many false positives that users, analysts, or administrators bypass it.

The one-class setup is especially relevant. In IAM and insider-threat settings, it is often easier to collect examples of one class, such as known abuse, known policy violations, or known benign workflows, than to obtain complete labels for all future behavior. The paper shows a concrete way to build useful classifiers under partial labelling, while still validating against manually inspected cases.

The paper also provides a useful research-positioning pattern: combine system measurement, explicit labelling rules, ML model design, and disagreement analysis against deployed tools. For PhD preparation, this is a strong template for security-ML work that must convince both ML reviewers and systems/security reviewers. It also connects directly to Kaafar's privacy measurement line of work: web-scale empirical privacy risk, usable defenses, and ML-assisted detection.

## 7. How To Use This Paper

- **Cite it for:** one-class learning for privacy/security detection; JavaScript tracker classification using code structure; empirical evidence that blacklist-based privacy tools can miss trackers and block functional scripts; the value of disagreement analysis between ML detectors and deployed security tools.
- **Do not cite it for:** current 2026 tracker prevalence, current performance of browser privacy tools, or a complete defense against all forms of web tracking and fingerprinting.
- **Follow-up reading:** papers on modern web tracking and fingerprinting, browser privacy interventions, adversarial ML for security classifiers, PU learning in security, and measurement studies that evaluate deployed privacy defenses at scale.
