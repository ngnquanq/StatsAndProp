# Paper Summary: Practical, Private Assurance of the Value of Collaboration via Fully Homomorphic Encryption

**Citation:** Hassan Jameel Asghar, Zhigang Lu, Zhongrui Zhao, and Dali Kaafar, 2025, Proceedings on Privacy Enhancing Technologies / PoPETs 2025. arXiv:2310.02563v3, 7 Oct 2024.  
**Source:** `/home/nhatquang/Desktop/HCMUS Course/PhD_Applications/Macquarie_Kaafar/kaafar-papers/pdfs/2310.02563-private-assurance-fhe.pdf`  
**One-line takeaway:** The paper proposes a practical protocol that lets two parties test whether combining labelled datasets will improve a neural-network model, while hiding private labels, models, and the resulting improved model, by combining TFHE with label differential privacy.

## 1. What Problem Is This Paper Solving?

The paper studies a pre-collaboration assurance problem: two parties may benefit from combining datasets, but they do not want to disclose sensitive labels, existing models, or the improved joint model before knowing whether the collaboration is worthwhile. The motivating example is malware classification. Antivirus company P1 has an existing model trained on its labelled malware dataset D1 and a labelled holdout set that reflects newer malware or class balance. Company P2 claims that adding its labelled dataset D2 will improve P1's model, but P2 does not want to reveal its labels before a formal agreement.

The straightforward cryptographic solution is to encrypt P2's labels and train the whole model under fully homomorphic encryption (FHE). The paper argues this is too slow for neural-network training. The goal is therefore narrower and more practical: reveal only whether training on D1 union D2 improves accuracy on P1's holdout set, while keeping D1, P1's holdout set, P1's model M1, P2's labels, and the updated model M2 private during the assurance stage.

## 2. Main Contributions

- It gives an interactive protocol for private pre-collaboration evaluation using TFHE, specifically fully homomorphic encryption over the torus, plus label differential privacy.
- It avoids end-to-end encrypted neural-network training by computing most forward and backward propagation in the clear, while only encrypting operations that depend on P2's private labels.
- It uses label differential privacy at the gradient level so P1 receives noisy gradients sufficient for training, but not exact label-derived gradients from P2's data.
- It analyzes a subtle "lack of domain knowledge" scenario: if P2 labels data obliviously, adding D2 should not help under balanced holdout and certain assumptions, but imbalanced or small D1 can still create apparent improvement.
- It implements the protocol with Zama's Concrete TFHE library and evaluates accuracy, runtime, randomized-response alternatives, and communication costs across several datasets.

## 3. Method Explained

**Intuition:** Since features are assumed public but labels are private, the expensive part should not be "encrypt the whole learning pipeline." P1 can compute neural-network activations and most derivatives because the feature vectors are known. The sensitive operation is where the label enters the gradient calculation. The protocol encrypts P2's labels, uses homomorphic operations only around the label-dependent gradient term, then adds calibrated label-DP noise before allowing the training process to continue in plaintext.

**Technical core:**

- Setting: P1 owns D1, a holdout set, and model M1. P2 owns D2. Features are shared openly; labels in D2 are hidden from P1. The model is a feedforward neural network trained with SGD, sigmoid activations, softmax output, and cross-entropy loss.
- Threat model: honest-but-curious parties. P1 should not learn P2's labels or M2; P2 should not learn D1, the holdout set, or P1's model parameters except coarse metadata such as batch size, number of epochs, and number of last-layer weights.
- Protocol: P2 sends encrypted one-hot labels for D2 under its TFHE key. For each batch, P1 computes last-layer derivative terms in the clear, multiplies them homomorphically with encrypted labels, and obtains an encrypted label-dependent gradient component. P2 also sends encrypted Gaussian noise vectors for a list of allowable sensitivity values. P1 selects the smallest sensitivity bucket covering the current batch sensitivity, blinds the encrypted noisy gradient, and sends it to P2 for decryption. P2 returns the decrypted but blinded noisy gradient. P1 removes the blind and proceeds with backpropagation in the clear.
- Privacy mechanism: the paper uses Gaussian label differential privacy. Because Concrete requires integer encoding, the authors avoid multiplying encoded Gaussian noise by encoded sensitivity directly; they show this can break DP. Instead, P2 precomputes noise for a discrete list of allowable sensitivity values.
- Security proof: the authors claim security in the real-ideal paradigm under the TLWE assumption and honest-but-curious behavior. P1 learns noisy gradients; P2 sees blinded quantities.

## 4. Experiments And Results

- **Data:** Iris, Seeds, Wine, Abrupto, Drebin Android malware, CIFAR-10, CIFAR-100, and Purchase-10. The main table reports detailed protocol results for Iris, Seeds, Wine, Abrupto, and Drebin; larger CIFAR/Purchase experiments are in the appendix and partly extrapolated.
- **Baselines:** plaintext M1 trained on D1; plaintext M2 trained on D1 union D2 without DP; PyTorch plaintext baseline; randomized response on labels; and comparison against reported end-to-end FHE neural-network training times from prior work.
- **Metrics:** holdout/test accuracy, training time, encrypted noise-list time, communication per epoch and total communication.
- **Key findings:** In an Abrupto case study with small imbalanced D1 and larger balanced D2, M1 averaged 0.704 accuracy while M2 averaged 0.912 on the holdout set. Across Table 4, the protocol can choose epsilon values where the private model's accuracy sits between M1 and M2, giving P1 evidence of improvement while preserving extra value for a later cleartext collaboration. The paper reports useful epsilon ranges around 0.3 to 0.5 across datasets, with Abrupto between roughly 0.15 and 0.5 and Drebin between roughly 0.3 and 0.5.

For accuracy examples, Iris improves from M1 0.7289 to M2 0.8467, while the protocol reaches about 0.8422 at epsilon 0.5 and 0.8554 at epsilon 100. Drebin improves from M1 0.8571 to M2 0.9470, while the protocol reports 0.8860 at epsilon 0.5, 0.9235 at epsilon 1, and 0.9476 at epsilon 100. Very large epsilon gives little privacy and mainly validates that encryption itself causes little accuracy loss.

Runtime is the central systems result. On small datasets, the protocol is much slower than plaintext but substantially faster than end-to-end encrypted training. Much of the cost comes from encrypting the t-list of noisy sensitivity values, which can be precomputed. For Iris, the paper compares against a prior HELib end-to-end encrypted neural-network setup estimated at at least 10,850 seconds for 50 epochs; their protocol takes around 4,200 seconds total, or about 150 seconds if noise lists are preprocessed. Communication is manageable per epoch: for example, Drebin is estimated at 53.70 MB per epoch, or 9.54 MB without the precomputed t-list.

Randomized response is faster but weaker for utility at privacy-relevant epsilon values. For Iris, Seeds, and Wine it often performs worse than M1 unless epsilon is high enough to reveal labels too faithfully. For Abrupto and Drebin, randomized response at epsilon 1 can beat M1, but the proposed protocol reaches the desired "between M1 and M2" assurance region at smaller epsilon.

## 5. Limitations And Risks

- The security model is honest-but-curious only. The paper explicitly leaves malicious parties as future work; P1 could lie about batch composition or otherwise manipulate noise requirements.
- The setting assumes features can be shared openly and only labels need protection. This is plausible for some malware or public-record settings, but not for many security, IAM, biomedical, or enterprise datasets where features themselves are sensitive.
- The implementation is not optimized: the authors reimplement neural-network training in NumPy/sklearn because they need access to intermediate gradients. They report it is 100-300x slower than PyTorch in plaintext and about 220x slower than PyTorch on Drebin.
- Concrete's integer-input requirement and precision handling limit very small epsilon values. The smallest tested total privacy budget is epsilon 0.1.
- The empirical scope is narrow for modern ML: shallow neural networks, tabular/small datasets in the main table, low CIFAR accuracy, and extrapolated times for larger datasets.
- The theoretical treatment of "oblivious" labels is limited to binary classification and 0-1 loss, with multiclass and broader classifier behavior left open.

## 6. Why This Matters For Nguyen Nhat Quang's IAM/security-ML PhD Direction

This paper is directly relevant to security-ML collaboration under privacy constraints. For IAM, insider-threat, malware, or enterprise telemetry research, the core bottleneck is often not model design but cross-organization data access: labels, incident annotations, policy outcomes, and analyst judgments are sensitive and expensive. The paper offers a concrete way to ask: "Can another organization's labelled events improve my detector before either side reveals labels or models?"

For a PhD proposal, the strongest connection is privacy-preserving evaluation of collaboration value. It complements security-ML work on federated learning, secure multiparty computation, and data markets by focusing on pre-contract assurance rather than full collaborative training. It also fits detector-sensitivity thinking: the protocol is not just about private training, but about deciding whether new labels change holdout performance enough to justify collaboration.

The caution for IAM is that the paper's assumption of public features is often too strong. In enterprise IAM logs, features such as role memberships, access times, resources, departments, and behavioral traces may themselves leak sensitive organizational structure. A useful research extension would relax this assumption, or split features into public, shareable, and private groups. Another extension is moving from honest-but-curious to malicious or strategically mislabelled parties, which is highly relevant when organizations have incentives to exaggerate dataset quality.

## 7. How To Use This Paper

- **Cite it for:** private pre-collaboration assurance; combining TFHE with label differential privacy; practical alternatives to end-to-end encrypted neural-network training; privacy-preserving evaluation of whether another labelled dataset improves a security classifier.
- **Do not cite it for:** full protection of feature privacy; malicious-party security; production-scale deep learning; proof that arbitrary data collaboration improves security-ML models.
- **Follow-up reading:** TFHE/Concrete documentation and TFHE schemes; label differential privacy; SecureML and FHE-based neural-network training; malicious-secure protocols for private ML; privacy-preserving data collaboration and data valuation.
