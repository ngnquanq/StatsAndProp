# Paper Summary: BlockJack: Towards Improved Prevention of IP Prefix Hijacking Attacks in Inter-Domain Routing Via Blockchain

**Citation:** I Wayan Budi Sentana, Muhammad Ikram, and Mohamed Ali Kaafar, 2021. Venue not stated in the inspected PDF; filename suggests arXiv:2107.07063.  
**Source:** `/home/nhatquang/Desktop/HCMUS Course/PhD_Applications/Macquarie_Kaafar/kaafar-papers/pdfs/2107.07063-blockjack-bgp-hijacking.pdf`  
**One-line takeaway:** BlockJack uses a permissioned blockchain, router-side monitoring, and automatic inbound filters to prevent BGP prefix hijacking without modifying the BGP protocol itself.

## 1. What Problem Is This Paper Solving?

The paper addresses IP prefix hijacking in Border Gateway Protocol (BGP), where an adversarial autonomous system (AS) advertises a prefix that belongs to another AS and can thereby attract, blackhole, inspect, or redirect traffic intended for the legitimate owner. The authors frame this as a persistent inter-domain routing security problem: BGP trusts route advertisements, and both malicious attacks and administrator mistakes can cause incorrect routing.

The paper positions BlockJack against three defense families. Machine-learning detection can struggle with rare hijacking samples and normal/attack similarity. Blacklist approaches can be too coarse because one malicious router may implicate a whole AS. RPKI/ROA/ROV provides an existing authorization path, but the authors argue that adoption, cost, and hierarchical trust remain practical deployment concerns.

## 2. Main Contributions

- The paper proposes BlockJack, a consortium-blockchain based system that stores prefix-to-origin-AS authorization data and uses that ledger to validate BGP route-origin claims.
- It separates blockchain operations from router/BGP operation through a Profiler and Dispatcher, preserving legacy BGP behavior and avoiding protocol modification.
- It introduces a neutralization mechanism that reacts to hijacking by issuing inbound filtering commands based on the invalid prefix and next-hop information.
- It evaluates BlockJack with Hyperledger Fabric, Quagga routers, Dockerized testbeds, and single-path, multiple-path, and random hijacking scenarios.
- It reports open-source availability at `https://github.com/budisentana/prefixHijackingPrevention.git`.

## 3. Method Explained

**Intuition:** BlockJack treats prefix ownership as a verifiable authorization record. A legitimate AS first registers its prefixes in a permissioned blockchain. Routers then monitor their BGP routing tables and check new externally learned prefixes against the blockchain. If a received prefix exists in the ledger but is announced by the wrong AS, BlockJack treats it as hijacking and installs an inbound filter to block the route advertisement from the suspicious neighbor.

**Technical core:**

- **Blockchain module:** Built on Hyperledger Fabric 2. It contains the smart contract/chaincode, Fabric CA, ledger, orderer, endorsers, and consensus mechanism. The ledger stores records including prefix, ASN, document type, and active status. The authors use Fabric's World State so current authorization data can be queried without traversing the full transaction log.
- **Profiler module:** Acts as the bridge between routers and blockchain. It creates admin and router credentials, stores them in wallets, exposes REST APIs, authenticates router requests, and forwards authorization or verification requests to the blockchain with the right credentials.
- **Dispatcher module:** Runs beside the router, not inside the BGP protocol loop. It has Monitor, Sender, and Verifier routines. Monitor queries the BGP table and extracts prefixes, next hop, and AS path. Sender handles locally originated prefix authorization and local ROA cache comparison. Verifier handles externally received prefix validation and local ROV cache comparison.
- **Race-condition design choice:** The authors deliberately avoid embedding blockchain logic into BGP messages or router internals. Authorization can be slow because it requires endorsement and committing a new block; keeping it independent from BGP update timing prevents the blockchain from blocking core routing operation.
- **AS-path-change resilience:** BlockJack stores only the prefix and origin AS in the blockchain, not the whole AS path. It uses AS path mainly to extract the origin and next hop. This avoids false invalidation when legitimate routing changes alter intermediate AS paths.
- **Verification outcomes:** A valid signal means the prefix and AS match ledger state. An invalid signal means the prefix exists but belongs to a different AS, indicating possible hijacking. An unknown signal means the prefix/AS pair is absent; in this implementation, unknown is treated as valid to allow non-BlockJack routers and reduce false positives.

## 4. Experiments And Results

- **Data/testbed:** The system uses Hyperledger Fabric containers, Node.js Profiler functions and REST APIs, Python plus shell scripts for Dispatcher routines, and Dockerized Quagga routers. Performance experiments ran on Ubuntu 18.04 with 2.7 GHz CPU and 16 GB RAM; resiliency experiments used 4 CPU cores and 128 GB RAM.
- **Baselines:** The paper does not include a direct quantitative baseline against RPKI, RouteChain, BGPcoin, or ML detectors. Comparison is mostly conceptual in the related work and design motivation.
- **Metrics:** Prefix authorization time, prefix verification time, hijack prepending time, and neutralization time.
- **Performance findings:** Authorization is expensive because each prefix addition commits a block. Average authorization is about 2.15-2.16 seconds per prefix: 216.21 seconds for 100 prefixes, 1,076.61 seconds for 500, and 2,154.32 seconds for 1,000. Verification is faster: 0.09-0.10 seconds per prefix, with 92.12 seconds for 1,000.
- **BGP interval analysis:** With a 30-second BGP UPDATE interval, the authors estimate BlockJack can authorize around 13 prefixes in one interval, which they compare to an average of 12 prefix announcements per AS origin. For verification, they estimate 300 concurrent updates could be checked in 27 seconds. However, first-time verification of an 850,000-prefix global table would take about 76,500 seconds, so local ROV caching is important.
- **Resiliency findings:** BlockJack neutralized adversarial prefixes that actually disrupted the valid-best route. Average neutralization times were 0.1516 seconds for single-path scenarios, 0.2362 seconds for multiple-path scenarios, and 1.0484 seconds for random attack scenarios. In a 50-router random scenario, the authors report 0.957 seconds to neutralize 12.04 attacks on average, equal to roughly 0.08 seconds per single attack.

## 5. Limitations And Risks

- The evaluation is a lab-scale Docker/Quagga testbed, not deployment on operational Internet routers.
- The paper does not quantify comparison against deployed RPKI/ROV infrastructure or other blockchain-BGP systems under the same workloads.
- Authorization latency is high, especially for large ASes or first-time onboarding; the paper itself estimates 17,550 seconds to authorize 8,125 prefixes in one large-AS scenario.
- Treating unknown prefixes as valid improves compatibility but weakens prevention when attackers use prefixes not present in the ledger.
- Global-scale verification needs caching; the raw ledger query rate is not enough for first-time validation of the full global routing table.
- The authors report that they could run 70 Docker routers but failed to configure them reliably using telnet because of network overload and timeout problems, which limits scaling evidence.

## 6. Why This Matters For Nguyen Nhat Quang's IAM/Security-ML PhD Direction

This paper is useful for a PhD direction that connects identity, authorization, and security automation. Although it is not an IAM paper in the enterprise-login sense, its core problem is identity and authority in distributed infrastructure: which AS is authorized to announce which IP prefix, how that authority is represented, and how enforcement happens when claims conflict.

For security-ML preparation, BlockJack is also a useful counterpoint to anomaly detection. The authors argue that ML-based BGP hijack detection is limited by class imbalance, scarce attack samples, and similarity between normal and malicious routing behavior. Their response is not a better classifier but a policy-backed verification architecture. That contrast can support a research narrative where ML is strongest when paired with explicit authorization, provenance, and enforcement mechanisms rather than used as the only line of defense.

For Nguyen Nhat Quang's likely research positioning, the paper can motivate hybrid systems that combine identity evidence, policy state, and detection signals. It suggests questions such as: when should security automation rely on learned anomaly scores, and when should it rely on cryptographic or ledger-backed claims? How should a system handle unknown entities without blocking legitimate interoperability? How can security controls be deployed around legacy infrastructure without forcing protocol redesign?

## 7. How To Use This Paper

- **Cite it for:** A blockchain-based BGP prefix-hijacking prevention architecture; the design choice to decouple blockchain validation from BGP protocol loops; use of Hyperledger Fabric for prefix-origin authorization; and empirical timing evidence for authorization versus verification costs.
- **Do not cite it for:** Proof that blockchain solves Internet-scale BGP security, production deployment readiness, superiority over RPKI in live networks, or ML detector failure in general. The evidence is testbed-based and comparative baselines are limited.
- **Useful quote-level idea to paraphrase:** BlockJack's conservative design preserves legacy BGP operation by keeping blockchain and routing environments independent while using router-side dispatchers for monitoring and filtering.
- **Follow-up reading:** RPKI/ROA/ROV deployment papers, RouteChain, BGPcoin/IPChain, and measurement studies of real BGP hijacking incidents. For an IAM/security-ML PhD proposal, also compare this with policy-enforcement architectures that combine identity registries, detection models, and automated response.
